**Ветка:** `main` + незакоммиченные изменения рабочего дерева

## 0. Как читать отчёт

- Все находки получены чтением текущего кода и конфигурации. Для каждой указан файл и строка.
- Метка **«подтверждено»** означает, что проблема видна в коде/конфиге без запуска.
- Метка **«среда»** означает, что эксплуатация зависит от конфигурации развёртывания (ingress, прокси, переменные окружения).
- Severity: **P0** — блокирует безопасную эксплуатацию, **P1** — серьёзный риск или сломанная функция, **P2** — риск/долг, **P3** — гигиена.
- Нумерация: `C-*` (critical), `H-*` (high), `M-*` (medium), `L-*` (low).

### Сводка

| Severity | Кол-во | Комментарий |
|---|---:|---|
| P0 | 6 | Требуют фикса до любого production-запуска |
| P1 | 20 | Фиксить в первые 2–4 недели |
| P2 | 16 | Плановые работы, 1–2 квартала |
| P3 | 11 | Гигиена и hardening |
| **Итого** | **53** | |

### Пять главных выводов

1. **Есть прямой путь к захвату платформы**: тенантный администратор с `user:write` может создать себе `is_superadmin=true` (`C-01`).
2. **Аутентификация устройств построена на заголовке, которым управляет клиент**, а mTLS на периметре не включён. Это даёт имперсонацию любого устройства и подпись произвольного CSR внутренним CA (`C-02`).
3. **SAML-реализация уязвима к XML Signature Wrapping**, а обязательные проверки (`InResponseTo`, `Audience`, `Destination`) сделаны опциональными (`C-03`).
4. **Мультитенантность ломается на входе**: поиск пользователя по `username`/`email`/`external_id` без tenant-фильтра (`C-04`).
5. **CSRF-защита нерабочая и одновременно ломает API-автоматизацию**: cookie `HttpOnly`, а фронтенд читает `document.cookie`; при этом middleware не освобождает запросы с API-ключом (`C-06`, `H-20`).

Отдельно: **JWT-ключи генерируются в каждом процессе** (`C-05`), поэтому при 4 воркерах × 2 репликах сессии «плавают». Это не только безопасность, но и причина случайных 401 в production.

## 2. Критические находки (P0)

### C-01. Повышение привилегий до SuperAdmin через создание пользователя

**Severity:** P0
**Статус:** подтверждено
**Компонент:** `backend/app/schemas/identity.py`, `backend/app/services/identity.py`, `backend/app/api/v1/endpoints/users.py`

**Доказательство**

```python
# backend/app/schemas/identity.py:95
is_superadmin: bool = False

# backend/app/services/identity.py:321
is_superadmin=payload.is_superadmin,
```

Эндпоинт создания пользователя защищён только `P.USER_WRITE`:

```python
# backend/app/api/v1/endpoints/users.py:127
dependencies=[Depends(require_permissions(P.USER_WRITE))],
```

Роль `ADMIN` (тенантный администратор) включает `USER_WRITE` (`backend/app/rbac/permissions.py`, блок `ADMIN`).

**Влияние**

Любой администратор тенанта создаёт пользователя с `is_superadmin=true` и получает:
- доступ ко всем тенантам (`TenantDep` для superadmin принимает произвольный `X-Tenant-Id`);
- платформенные эндпоинты (`/tenants`, RBAC, лицензии);
- полный обход tenant isolation.

Это полный захват платформы из одной тенантной учётки.

**Исправление**

1. Удалить `is_superadmin` из `UserCreate`/`UserUpdate` полностью.
2. Назначение superadmin — отдельный эндпоинт `POST /platform/users/{id}/promote` с `require_superadmin()` и обязательным MFA/step-up + записью в audit.
3. В `UserService.create` явно игнорировать/запрещать поле, даже если оно придёт в payload.
4. Добавить регрессионный тест: `ADMIN` с `USER_WRITE` не может создать superadmin (ожидаем 422/403).

**Effort:** 0.5 дня.

### C-02. Аутентификация устройства по заголовку `X-Device-Cert-Fingerprint` без привязки к TLS

**Severity:** P0
**Статус:** подтверждено (код) + среда (ingress/nginx)
**Компонент:** `backend/app/api/v1/endpoints/agent.py`, `frontend/nginx.conf`, `deploy/helm/ofme/**`

**Доказательство**

```python
# backend/app/api/v1/endpoints/agent.py:38
FingerprintHeader = Annotated[str | None, Header(alias="X-Device-Cert-Fingerprint")]
DeviceIDHeader = Annotated[uuid.UUID, Header(alias="X-Device-Id")]

# :58-79 — устройство определяется по двум заголовкам, которые присылает клиент
fingerprint = x_device_cert_fingerprint or x_client_cert_fingerprint
...
DeviceCertificate.device_id == device.id,
DeviceCertificate.fingerprint_sha256 == normalised,
```

При этом:
- `frontend/nginx.conf`, `location /api/`, пробрасывает запросы в `ofme-api:8000` и **не удаляет** `X-Device-*`;
- `deploy/helm/ofme/templates/ingress.yaml` не содержит `nginx.ingress.kubernetes.io/auth-tls-verify-client` и `auth-tls-secret`;
- `deploy/helm/ofme/values.yaml` (блок `ingress.annotations`) тоже не настраивает mTLS.

То есть в типовом развёртывании заголовок может выставить любой, кто достучался до `/api/v1/agent/*`.

**Влияние**

Зная `X-Device-Id` (UUID устройства) и fingerprint любого активного сертификата (fingerprint не является секретом: он хранится в БД и доступен через `GET /api/v1/certificates` при `CERT_READ`), атакующий может:

1. **Выдавать себя за устройство**: получать полный desired config (firewall/NAT/alias/interface/route/VLAN/VPN/SD-WAN), pending commands, отправлять heartbeat и `command_results`.
2. **Использовать CA как signing oracle**: `POST /api/v1/agent/certificate/renew` принимает произвольный CSR и выпускает сертификат с `validity_days` до 3650 (`agent.py:491-510`, `pki/ca.py:132-210`). CSR подписывается атакующим, CN/SAN подставляет сервер — но ключ остаётся у атакующего. Дальше это уже легитимный клиентский сертификат для mTLS.
3. **Инжектить команды/телеметрию** и искажать состояние флота.

**Исправление (обязательный минимум)**

1. Включить mTLS на периметре: `auth-tls-verify-client: optional` + `auth-tls-secret`, передавать `ssl-client-verify`/`ssl-client-fingerprint`; fingerprint брать **только** из TLS-контекста, не из заголовка.
2. В nginx явно чистить входящие `X-Device-*`/`X-Client-*`:
   ```nginx
   proxy_set_header X-Device-Cert-Fingerprint "";
   proxy_set_header X-Client-Cert-Fingerprint "";
   proxy_set_header X-Device-Id "";
   ```
3. В коде: если TLS-терминация не подтверждена (`settings.AGENT_MTLS_TERMINATED=true` + доверенный прокси), отклонять запросы с этими заголовками.
4. Для `certificate/renew` требовать proof-of-possession: подпись CSR-ключа над nonce, выданным сервером, и/или подпись текущим ключом.
5. Ограничить `validity_days` значением `PKI_DEVICE_VALIDITY_DAYS` (не позволять клиенту выбирать 10 лет).

**Effort:** 2–3 дня (инфра + код + тесты).

### C-03. SAML: XML Signature Wrapping, необязательные проверки, XXE

**Severity:** P0
**Статус:** подтверждено
**Компонент:** `backend/app/integrations/saml.py`

**Доказательство**

Парсинг без ограничений:

```python
# backend/app/integrations/saml.py:199
root = etree.fromstring(raw)
```

Проверка подписи и последующее извлечение assertion — из разных элементов:

```python
# :238-256
def _verify_signature(self, root):
    candidates = []
    if root.find("ds:Signature", NS) is not None:
        candidates.append(root)
    assertion = root.find("saml:Assertion", NS)
    if assertion is not None and assertion.find("ds:Signature", NS) is not None:
        candidates.append(assertion)
    ...
    XMLVerifier().verify(element, x509_cert=cert)
    return          # результат verify (signed_xml) игнорируется

# :211-213
assertion = root if etree.QName(root).localname == "Assertion" else root.find(
    "saml:Assertion", NS
)
```

`root.find("saml:Assertion")` возвращает **первый** assertion. Если подписан второй (или подпись лежит на копии в `Extensions`), проверка проходит, а читается неподписанный assertion — классический XSW.

Дополнительно:

```python
# :259-266 — InResponseTo проверяется только если он есть
if expected_request_id and in_response_to and in_response_to != expected_request_id:
    ...

# :283 — Audience проверяется только если список непустой
if audiences and self.entity_id not in audiences:
```

`Destination` не проверяется вообще.

**Влияние**

- Подмена identity в SAML-ответе → вход под произвольным пользователем (включая superadmin), если IdP-подпись можно «переложить».
- Отсутствие обязательного `InResponseTo` позволяет принимать unsolicited-ответы (login CSRF/фиксация сессии).
- Парсер не настроен явно: поведение зависит от версии `lxml` и системного `libxml2`; при `resolve_entities=True` (или смене версии) появляется XXE/SSRF, а expansion-атаки остаются возможны. Для SAML парсер должен быть захардкожен, а не наследовать дефолты.

**Исправление**

1. Использовать **только** `signed_xml`, возвращённый `XMLVerifier().verify(...)`, и извлекать claims из него. Никогда не читать оригинальный `root` после проверки.
2. Требовать ровно один `Assertion`; отклонять `Assertions > 1`, `Extensions` с assertion, вложенные assertion.
3. Парсер: `etree.XMLParser(resolve_entities=False, no_network=True, dtd_validation=False, load_dtd=False, huge_tree=False)`.
4. Сделать обязательными: `InResponseTo == request_id`, `Destination == ACS URL`, `Audience == SP entity_id`, `NotBefore/NotOnOrAfter`, `SubjectConfirmationMethod == bearer`.
5. Replay-cache должен **fail closed**: сейчас при ошибке Redis `_remember_assertion` возвращает `True` (`saml.py:120-130`).
6. Добавить тест на XSW (подписанный «безобидный» assertion + неподписанный целевой).

**Effort:** 3–4 дня.

### C-04. Кросс-тенантный вход: `external_id` и `username` ищутся без tenant-фильтра

**Severity:** P0
**Статус:** подтверждено
**Компонент:** `backend/app/services/auth.py`, `backend/app/repositories/identity.py`

**Доказательство**

```python
# backend/app/services/auth.py:140-147
tenant_id = await self._resolve_tenant(tenant_slug)
self.users.tenant_id = tenant_id
user = await self.users.get_by_username(username, tenant_id)
...
if user is None and tenant_slug is None:
    # SuperAdmin fallback: unique usernames/e-mails across the platform.
```

`_resolve_tenant(None)` возвращает `None` (`auth.py:79-81`), а `get_by_username(..., None)` не добавляет фильтр:

```python
# backend/app/repositories/identity.py:19-25
stmt = select(User).where(User.username == username, User.deleted_at.is_(None))
tid = tenant_id or self.tenant_id
if tid is not None:
    stmt = stmt.where(or_(User.tenant_id == tid, User.tenant_id.is_(None)))
return (await self.session.execute(stmt)).scalars().first()
```

То же для `external_id` при SSO/LDAP:

```python
# backend/app/services/auth.py:552-560
select(User).where(
    User.external_id == external_id,
    User.auth_provider == provider,
)
```

**Влияние**

1. **Неоднозначность логина**: если `admin` существует в нескольких тенантах, выбирается первый по порядку БД. Пользователь тенанта A может попасть в тенант B (если пароли совпали) либо получить отказ/блокировку из-за чужой учётки. Это нарушение изоляции и потенциальный account takeover при совпадении паролей.
2. **SSO/LDAP**: `external_id` (LDAP DN, OIDC `sub`, SAML NameID) уникален только внутри IdP. Два тенанта с одинаковым `sub` (например, `admin` в двух Keycloak realms) → вход в чужую учётку. Это уже прямая эскалация между тенантами.
3. Fallback «superadmin по username без tenant» расширяет поверхность атаки на платформенную учётку.

**Исправление**

1. Сделать tenant обязательным для всех входов: subdomain (`acme.ofme.example.com`), отдельный `tenant` в форме, либо `X-Tenant` на странице логина. Отказ, если tenant не определён (кроме явного platform-login).
2. Уникальные индексы: `UNIQUE (tenant_id, username)`, `UNIQUE (tenant_id, email)`, `UNIQUE (tenant_id, auth_provider, external_id)`.
3. В `_provision_external_user` всегда фильтровать по `tenant_id`; при коллизии `external_id` в другом тенанте — ошибка, а не «первый найденный».
4. Убрать «superadmin fallback» или ограничить его отдельным эндпоинтом `/auth/platform-login` с rate-limit и MFA.
5. Тест: два тенанта с одинаковым `username`/`external_id` — вход строго в свой.

**Effort:** 2 дня + миграция индексов.

### C-05. JWT-ключи генерируются в каждом процессе → сессии невалидны между воркерами и репликами

**Severity:** P0 (доступность + безопасность)
**Статус:** подтверждено
**Компонент:** `backend/app/core/security.py`, `deploy/helm/ofme/templates/api.yaml`, `deploy/helm/ofme/templates/configmap.yaml`

**Доказательство**

```python
# backend/app/core/security.py:44-70
if _get_settings().JWT_PRIVATE_KEY_PATH and Path(...).exists():
    _private_key = Path(...).read_bytes()
else:
    private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
    ...
    if _get_settings().ENVIRONMENT != "production":
        Path(".dev_jwt_private.pem").write_bytes(_private_key)
```

Helm запускает 4 воркера на под и 2 реплики:

```yaml
# deploy/helm/ofme/templates/api.yaml:56-64
- --workers
- "4"
```

```yaml
# deploy/helm/ofme/values.yaml
api:
  replicaCount: 2
```

`configmap.yaml` не задаёт `JWT_PRIVATE_KEY_PATH`/`JWT_PUBLIC_KEY_PATH`, `secret.yaml` их тоже не содержит.

**Влияние**

- В production каждый из 8 процессов генерирует свой RSA-ключ при первом использовании. Токен, выданный воркером №1, отвергается воркером №2 → случайные 401, «мигающие» сессии, невозможность горизонтального масштабирования.
- После рестарта пода все сессии инвалидируются.
- В non-production ключ пишется в `.dev_jwt_private.pem` внутри контейнера (не шарится, попадает в слой FS).
- Если кто-то «решит» проблему, отключив проверку подписи, — это уже полный обход аутентификации.

**Исправление**

1. Обязательные `JWT_PRIVATE_KEY_PATH`/`JWT_PUBLIC_KEY_PATH` из Secret (Helm `secrets.existingSecret`).
2. В `ENVIRONMENT=production` **падать при старте**, если ключей нет (fail fast), вместо генерации.
3. Для ротации — `kid` в заголовке JWT и набор ключей (JWKS), чтобы можно было менять ключ без разлогина.
4. Убрать запись `.dev_jwt_private.pem` в файловую систему (или в явно заданный temp с правами 0600).
5. Добавить тест: два процесса с одним ключом принимают токен друг друга; без ключа в prod — `RuntimeError`.

**Effort:** 1–2 дня.

### C-06. CSRF-защита нерабочая: `HttpOnly` cookie + чтение из `document.cookie`; ломает и UI, и API-клиентов

**Severity:** P0 (функциональность + безопасность)
**Статус:** подтверждено
**Компонент:** `backend/app/observability/middleware.py`, `frontend/src/api/client.ts`, `backend/app/api/v1/endpoints/auth.py`

**Доказательство**

Сервер ставит CSRF-cookie как `HttpOnly`:

```python
# backend/app/observability/middleware.py:196-205
response.set_cookie(
    key=CSRF_COOKIE_NAME,
    value=new_token,
    max_age=CSRF_COOKIE_MAX_AGE,
    httponly=True,
    ...
)
```

Фронтенд пытается прочитать её из JS:

```ts
// frontend/src/api/client.ts:95-102
const csrfCookie = document.cookie
  .split("; ")
  .find(row => row.startsWith("ofme_csrf_token="))
  ?.split("=")[1];
if (csrfCookie) {
  config.headers.set("X-CSRF-Token", csrfCookie);
}
```

`document.cookie` **никогда** не увидит `HttpOnly`-cookie → заголовок не отправляется.

Логика middleware:

```python
# :192-217
cookie_token = request.cookies.get(CSRF_COOKIE_NAME)
if not cookie_token:
    response = await call_next(request)   # первый запрос пропускается
    ... set_cookie(...)
    return response
header_token = request.headers.get(CSRF_HEADER_NAME)
if not header_token or not _verify_csrf_token(cookie_token, header_token):
    return JSONResponse(status_code=403, ...)
```

**Влияние**

1. **UI**: после первого мутирующего запроса (например, создания устройства) cookie появляется, и все последующие `POST/PUT/PATCH/DELETE` получают `403 csrf_failed`. Продукт фактически неработоспособен для повторных операций.
2. **API-автоматизация**: middleware не освобождает запросы с `Authorization`/`X-API-Key`, хотя docstring обещает обратное (`middleware.py:151-158`). Любой скрипт с API-ключом после первого запроса получает 403, если не пришлёт cookie, которую ему никто не выдавал.
3. Команда, скорее всего, «починит» это отключением CSRF — и тогда останется реальная CSRF-уязвимость при cookie-аутентификации.

**Исправление**

1. Выбрать одну модель:
   - **cookie-only**: `HttpOnly` для access/refresh, CSRF-cookie — **не** `HttpOnly`, `SameSite=Strict` (или `Lax` + Origin-check), `Secure`; фронтенд читает и отправляет токен.
   - **bearer-only**: не ставить auth-cookies, не требовать CSRF, хранить токены в памяти.
2. В middleware освобождать запросы, аутентифицированные заголовком (`Authorization`, `X-API-Key`) — CSRF актуален только для cookie.
3. Добавить проверку `Origin`/`Referer` для cookie-мутаций.
4. Не возвращать `access_token`/`refresh_token` в теле ответа при cookie-режиме (`LoginResponse` сейчас содержит оба).
5. Тест: логин → 5 мутаций подряд → все 200; API-ключ → мутации без CSRF → 200; cross-origin POST без токена → 403.

**Effort:** 1–2 дня (плюс правки тестов и фронтенда).

## 6. Что сделано хорошо (не переделывать)

- **Tenant isolation на уровне зависимостей** (`api/deps.py`, `get_tenant_id`) — корректно запрещает cross-tenant для не-superadmin.
- **Единый обработчик ошибок** (`main.py`) не отдаёт stack trace и внутренние сообщения в 500.
- **Пароли**: Argon2id, политика сложности, lockout, MFA backup-коды хешируются.
- **Refresh-токены** хешируются с pepper, хранятся как записи с `jti`/`expires_at`.
- **Агент**: жёсткий whitelist команд, нет generic shell (`CommandRunner.php`).
- **PKI**: ключ CA пишется с `chmod 0600`, CSR-подпись проверяется, сертификат содержит tenant OID.
- **Зависимости backend** в основном запинены, есть `pip-audit`/`trivy` в CI (пусть и `allow_failure`).
- **Фронтенд**: нет `dangerouslySetInnerHTML`, CSP без `unsafe-inline` для скриптов, токены не в `localStorage`.
- **Инфраструктура**: Helm с `runAsNonRoot`, `readOnlyRootFilesystem`, `drop: ALL`, NetworkPolicy default-deny, отдельные health/readiness probes.
- **Новые фичи** (maintenance, reports, bulk, traffic) следуют существующим паттернам: сервис + UoW + audit + tenant-scope.

## 9. Приложение A. Быстрые проверки (для верификации после фиксов)

```bash
# 1. C-01: ADMIN не должен создавать superadmin
curl -s -X POST http://localhost:8080/api/v1/users \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"username":"evil","email":"evil@example.com","password":"Str0ng!Passw0rd","is_superadmin":true}'
# ожидаем 422 (поле неизвестно) или 403

# 2. C-06: пять мутаций подряд с cookie-сессией
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:8080/api/v1/sites \
    -H "Content-Type: application/json" -b cookies.txt \
    -d "{\"name\":\"s$i\",\"code\":\"S$i\"}"
done
# ожидаем 200/201 каждый раз

# 3. C-02: заголовок не должен работать без mTLS
curl -s -o /dev/null -w "%{http_code}\n" \
  http://localhost:8080/api/v1/agent/config \
  -H "X-Device-Id: a117c5b4-c097-428a-95c3-a048c30c320e" \
  -H "X-Device-Cert-Fingerprint: deadbeef"
# ожидаем 401/403

# 4. H-16: метрики закрыты
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/metrics
# ожидаем 401/403 (или connection refused на отдельном порту)

# 5. C-05: два воркера принимают один токен
for i in 1 2 3 4 5 6 7 8; do
  curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/api/v1/auth/me \
    -H "Authorization: Bearer $ACCESS_TOKEN"
done
# ожидаем 200 во всех случаях
```
